# contextdb 2: working in `v2/`

This workspace is contextdb 2: an embedded SQL database kept in one folder, the `contextdb`
program over it, and the storage library both are built on. Repository-wide policy (commit
messages, licence, contribution rules) is in the root [`AGENTS.md`](../AGENTS.md) and is not
repeated here; every command is in [`README.md`](README.md).

## Packages and parts

| Package | What it is |
|---|---|
| `contextdb/` | The library. Its public calls are the re-exports in `contextdb/src/lib.rs`; `contextdb/README.md` is also its documentation page, and the program in it is compiled as a documentation test. |
| `contextdb-cli/` | The `contextdb` program, a SQL shell. Every statement and command goes through the library's public calls; it never opens a store's files itself. |
| `redb/` | redb 4.1.0 with the changes listed at the top of `redb/README.md`. It keeps its own manifest and lock file and is not a workspace member. |

The library is thirteen parts, one folder each under `contextdb/src/`:

| Part | Does | Never |
|---|---|---|
| `types` | `Value`, the one `Error`, ids, table and event descriptions | holds behaviour: reads no store, checks no rule of a table, decides no answer; the one refusal it makes is `typed`, which turns away a value that is not of its column's type |
| `system` | time through `Clock`, and the maintenance worker's thread and condition-variable wait | implements a maintenance step |
| `memory` | the budget and the reservations taken from it | allocates for another part: it counts what they are about to take and says no first |
| `sql` | grammar, parser, planner: text to a statement, a statement to a plan; reads every table option and column constraint (including `STATE MACHINE`, `PROPAGATE`, `CONTEXT_ID`, `SCOPE_LABEL`, `ACL` and the `ALTER TABLE` forms); `sql::formula` reads a rank formula, the one reading of it | touches storage or knows what a table holds |
| `store` | the folder and data file, how each record is keyed, a row's large text, JSON and vectors kept beside the row in slices (text and JSON compressed there when that saves an eighth, `store/record.rs`), views of one moment, the reader files (one in `readers/` per reader that is inside a statement, naming the commit it reads) and the locks | interprets SQL or a table's rules |
| `schema` | table, event and schedule declarations: checking, storing, printing them back; the `Rules` of a table (references, immutable columns, propagation, the Context, label and access columns, counts) worked out once from its declaration, and `ALTER TABLE` and `DROP` (`schema/alter.rs`) with the refusals of what a change would leave dangling | changes a row |
| `query` | answers a SELECT (joins, grouping, set operations, subqueries, graph patterns and a vector search included) and `EXPLAIN` of any statement; holds the one expression evaluator, the one reader of a statement's `WHERE` (`query/filter.rs`: `Reading`, `Part`, `Case` and `Fact`, what a filter fixes of each column; the index chooser, the vector search's partitions and pairs, the counts answered without rows and the grouped kept counts all take their facts from it, and `filter::read` is the one reader of what a `WHERE` fixes of a table's columns: `search::bound` and `join::firsts` take whole parts of a `WHERE` and read no table column, and any other reading is a second path) and the one filter of who may see a row (`Reader`, `Visible`, in `query/visible.rs` with its tests in `contextdb/tests/visibility.rs`); a narrowed `Reader` is handed to every read and every search; counts the rows it reads (and the index entries a count is answered from) and a search's distance evaluations; answers `SHOW VECTOR_INDEXES`, `SHOW VECTOR_PARTITIONS` and `explain` (which takes the `Reader`) from the vector part's small records, and `SHOW STATEMENT_STATISTICS` (`runs` in `query/inspect.rs`) from the records in `database/statements.rs` | changes anything |
| `write` | applies INSERT, UPDATE and DELETE to a change set; checks types, NOT NULL, the primary key (also the hidden key of a table with none) and UNIQUE rules, `IMMUTABLE`, the state machine, references both ways, a `DAG`, and the rows a `PROPAGATE` moves in the same statement; asks `Visible` whether the handle may write the row; keeps index entries and row counts; checks at commit what only the whole transaction answers (`write/commit.rs`) | returns a query's result to a caller |
| `database` | the handle a store is opened for writing with, the handles narrowed from it (`scoped_with_constraints`), the refusal of a statement by the kind of handle (`Database::execute` refuses what `Plan::admin_only` names when the `Reader` is narrowed; the Rust call `set_memory_limit` makes the same refusal; `run_maintenance_cycle` maintains the whole store but withholds its report counts on a narrowed handle), the record of statements (`database/statements.rs`: one line for each form of SELECT, INSERT, UPDATE and DELETE, in memory only, sized by `SET STATEMENT_STATISTICS_LIMIT`, emptied by `RESET STATEMENT_STATISTICS`), its transactions and their numbers, row guards, the one commit function (where two transactions' conflicts are decided: first commit wins, no waiting); `table_meta`, `declaration`, `declared_events` and `declared_table`; `run_maintenance_cycle` (one step for every partition with work, then expiry through bounded row-removal commits and a bounded partial-tail sealing commit, each worked out with no lock held and committed through the one commit function); `explain` | has a second way to commit |
| `read` | bounded sessions with result/work/time/memory limits, cancellation and inline progress, over the one read core; `explain`; the optional opaque writer-request channel and its joined listeners | changes anything a writer stored |
| `vector` | the blocks of a VECTOR column (a one-byte copy of every vector), the lists of vectors not yet in a block, the column's partitions and their count, the IVF of a partition (its centroids, a one-bit binary code of every slot, the partition's mean), search over them (every slot, or the binary codes of the nearest groups and of the tail, then the slots those keep), building an IVF in steps and putting it in force, sealing, and what inspection reads | decides which rows a reader may see: `query` tells it, row by row, and a row is in an answer only with the distance `query` worked out from the row's stored vector; reads a clock, takes the commit lock, or starts a thread |
| `events` | dispatches changed rows to registered host callbacks inside the committing transaction, bounds cascades, and holds the callback handle to that transaction and reader | commits, changes reader permissions, or delivers external notifications |
| `maintenance` | the one finite cycle: one step for every due build, due retained rows removed in bounded commits, then at most 4,096 unindexed vectors sealed for a caller or timer cycle; its report; whole-store verification and content-byte accounting in `verify.rs` | starts a thread or reads machine time directly; expiry asks `system::now_millis` through the open handle's `Clock` |

The files of `vector/`, each as its opening comment says:

- `slot.rs`: one vector as a block keeps it (a scale, a rounding error and a signed byte for each number), the range a search gets from it, and the distance every answer is ordered by; `Reduced`, the one place that turns a vector into one byte a number for a column declared `SQ8`.
- `block.rs`: the slots of as many vectors of one partition as fit in the block's bytes, each with the key of its row.
- `directory.rs`: the partitions of a VECTOR column, one record for each key tuple under which a row has a vector.
- `ivf.rs`: the IVF of a partition (its slots sorted by the centroid each is nearest, packed into full blocks, with the centroids, the place where each group begins and a binary code of every slot) and the partition's mean; written once by the build that made it and never changed.
- `binary.rs`: one vector as a binary code keeps it (a bit for each number and a factor, taken from a reference: the centroid of its group, or the partition's mean for a tail block), and the range a search gets from a binary code; the counting loop.
- `train.rs`: finding centroids, the arithmetic of a build over slots alone; nothing there reads a store.
- `build.rs`: when an IVF is due, the record of how far a build has come, and the steps that find centroids and say which group each slot goes to.
- `pack.rs`: the last steps of a build: packing the slots of each group into the blocks of the new IVF with a binary code of each, measuring how far a search scans and how wide a binary code's estimate is taken to be, and putting the IVF in force.
- `search.rs`: the one search, and the plan it runs: scores the rows in no block exactly, screens the slots of the selected partitions (every slot of a partition searched whole; of one searched by its nearest groups, the slots its binary codes keep), asks for the true distance of the rows that can reach the answer, and proves the answer.
- `seal.rs`: moving the vectors on the unindexed lists into blocks.
- `unindexed.rs`: what a commit's row changes mean for the vector part, worked out once inside the commit function.
- `tally.rs`: the partitions a transaction's statements have made and emptied, so that the statement that would give a column one partition too many is refused when it runs.
- `inspect.rs`: what inspection reads of a VECTOR column, its partitions as their records describe them; no block, no centroid and no row.

## Where the parts meet

A part reaches another only through what that part makes visible: the `pub(crate)` items of its
`mod.rs`, and for `sql` its `ast` and `plan` modules. A statement form this version does not have is refused in `sql` (`not_supported` in `sql/mod.rs`, called by the parser and the planner), before any table is looked up. The types handed across:

| Type | Defined in | Who takes it |
|---|---|---|
| `Plan` (with `Effect`, `Expr`, `Statement`) | `sql` | `schema`, `write` and `query` each take a planned statement |
| `Read` (implemented by `View`, the store as of one commit, and by `ChangeSet`) | `store` | `query` and `write` read through it |
| `ChangeSet`, everything one transaction means to change, held in memory over a `View` | `store` | `schema` and `write` stage into it; `database` hands it to `Store::commit` |
| `Store`, `Key`, `Row`, `Cell`, `TableId`, `IndexId` | `store` | `database` and `read` open a `Store`; the rest name rows and indexes |
| `Budget`, `Reservation` | `memory` | everything whose memory grows with data holds a reservation |
| `Catalog`, `Table`, `Rules` | `schema` | `query`, `write`, `database` and `read` look tables up in it; a table's references, immutable columns, propagation edges and its Context, label and access columns are fields of `Table::rules`, the other options are in `Table::meta` |
| `Reader`, `Visible` | `query` | `database` and `read` make a `Reader` for a handle (what it is narrowed to); `write` and `query` ask `Visible` before any row is shown or staged |
| `eval`, `rows_for_write` | `query` | `write` finds the rows of an UPDATE or DELETE with `query::rows_for_write`, a batch at a time, and works out values with `query::eval` |
| `Asked`, `EvalContext`, `reads`; `Visible::new`, `Visible::reads`, `Visible::may_write`, `Reader::admin` | `query` | `write` is also handed these to evaluate and to ask who may write; from `store` it uses `Beside`, `Entry`, `EntryShape`, `KEY_LIMIT`, `RowGuard`, `View` and `CountId`, and from `schema` the fields of `Table` |
| `QueryResult` | `query` | `database` and `read` build it and hand it to the caller |
| `PhysicalPlan::VectorSearch`; `Expr::Distance`, `Expr::Row`, `Expr::InList` | `sql` | `query` runs the search, puts its distance wherever the select list writes `<=>`, and evaluates `IN` lists and row values |
| `VectorColumn` (a VECTOR column's number, partition key, limit, mode, quantization, `INDEXING_THRESHOLD` and compaction, with the numbers in force), from `Table::vectors`, `Table::vector` and `Catalog::vector` | `schema` | `query`, `write` and `vector` |
| `staged`, `vectors` and `vector_number` on `Read`; `put_vector`, `delete_vector` and `put_vector_number` on `ChangeSet`; `VectorRecord`, `VectorNumber`, `VectorId` | `store` | `vector` reads and stages its blocks, unindexed entries, partition entries and counts through them; `store` keeps them and never interprets one |
| `search`, `plan`, `Nearest`, `Route`, `distance` | `vector` | `query` calls `search` with the partitions the filter selects, the mode in force, the column's declaration and whether the statement has a filter on rows, and answers it, row by row, with `distance` of the row's stored vector, or with nothing for a row that is gone, filtered out or has no vector; `search` answers nothing at all only when INDEXED is refused (a selected partition is not usable, or a filter on rows leaves the index nothing to choose among), which `query` turns into the refusal. `plan` settles what a search does with each partition, from small records alone, and `search` runs exactly that plan, so `explain` cannot disagree with it |
| `Tally`, the partitions a transaction has started and emptied | `vector` | `database` holds one beside each change set and forgets a refused statement's part of it; `write` notes every row it stages, including the rows a propagation moves, and settles the tally once per statement after following, which is where a statement over `MAX_PARTITIONS` is refused; `vector::tally::tuples` decides which rows have an entry (none for a row in an `EXCLUDE VECTOR` state, with a NULL vector, or missing) |
| `track_unindexed`, `seal` | `vector` | `database` calls `track_unindexed` inside the one commit function, after the commit's other rules have passed; `maintenance` calls `seal` |
| `unindexed_work`, `prepare`, `stage_step`, `stage_refusal`, `progress` (and the values they return) | `vector` | `maintenance` lists the partitions with work, has a step worked out with no lock held, and stages it through the one commit function; a step the memory limit refuses is recorded, not returned |
| `partitions`, `Inspected`, `State` | `vector` | `query` answers the two SHOW statements and `explain` with them |
| `Reduced` | `vector` | `write` gives a column declared `SQ8` the vector `Reduced` makes of the one written, and hands the store its scale and codes with the row (`store::Compact`) |
| `cycle`, `MaintenanceReport` | `maintenance` | `database` runs one cycle for `run_maintenance_cycle` and commits it through the one commit function |
| `Store::count_cache_under` | `store` | `database` has the store check its page cache against a new limit, on the one path that sets the memory limit |

## How tests are written here

- A test goes through a public call of the library or through the built program, never an inner item.
- SQL behaviour is a script under `contextdb/tests/sql/` with its expected output; tests that kill a process and reopen the store live in `contextdb/tests/crash/`.
- An inner test, in a file named `tests.rs` under `src/`, exists only for pure arithmetic or for bytes damaged on disk that no public call can write. When a fix round is green, tests that overlap are merged, as cases of one table, before the branch lands.
- A test asserts states, values, error kinds and counts. It never decides by elapsed time and never sleeps to wait: it waits for an event a process announces, or reads a count. Every promised speed or size is guarded by a test that counts the work (rows read, distances worked out, bytes), never one that times it.
- Its data is fixed, and each test has its own store folder (`support::folder` in `contextdb/tests/support/mod.rs`).
- Nothing is retried (`.config/nextest.toml` sets `retries = 0`) and no test is ignored.
- The default nextest filter omits the million-row load, million-row append and both sighting-scale tests. Pull requests run the 100,000-sighting test and million-row load in release mode. Scheduled and manually dispatched runs use the `nightly` profile for the million-row load and append, and a separate release job for the million-sighting test; they also run 16 mutation shards. Each workflow job has its own timeout (20 minutes for the test matrix, 30 for release and scale), not a promised whole-workflow runtime. See [`README.md`](README.md#hosted-checks) for commands and the instruction-cost gate.

Two lint settings hold this up:

- `clippy.toml` refuses `std::thread::sleep`, starting a thread, `Instant::now`, `SystemTime::now` and `uuid::Uuid::new_v4`: the engine sleeps only in `system::pause` between tries of a wait the caller bounded; the worker waits on its condition variable; the engine starts maintenance and request-listener threads only in `system::launch`, draws no random number, and reads time only through `Clock`.
- `Cargo.toml` denies `clippy::iter_over_hash_type` for both members: a hash map is walked in a different order in every process, so nothing is built by walking one.

## Making a change

A defect is fixed by changing or removing code where its promise is owned, not by adding
around it. Before writing a line:

1. **Name what broke.** Find the row of "Invariants and the tests that guard them" that the
   defect breaks, or write the one sentence that should be a row. A defect that cannot be
   said in one sentence is not understood yet.
2. **Find the part that owns it** in the parts table, and fix it there, once. A check added
   at each caller, a flag, an option, a retry, a second path or a special case for one input
   means the fix is in the wrong part: stop and look again.
3. **Fix the kind, not the one.** Look for the same mistake beside it in that part; a defect
   is usually one of several of its kind.
4. **Remove what the fix makes unnecessary** in the same change: a guard an earlier fix
   added, a helper nothing calls, a comment that is no longer true. Prefer making a wrong
   state impossible where it enters (a type, a limit, a refusal when it is written) to
   handling it wherever it could arrive.
5. **Extend a test that guards the invariant** rather than add one beside it. A new test is
   for an invariant, or a case of one, that no test covers, and the table's row names it. A
   test changes only when the promise it states has changed, never to let a fix pass.
6. **Keep it small.** A fix that adds more than about fifty shipped lines, or changes more
   than two parts, is a redesign: stop, and write in the change's description what the
   invariant is and why its owner cannot hold the fix.

The check holds the line where no judgement is needed (`.github/workflows/check.yml`):

- It states three sizes: `SHIPPED_LINES` (the shipped code, rounded up to 500 lines), `TESTS`
  (the tests, rounded up to 10) and `TEST_LINES` (the lines of tests, rounded up to 500). Each
  holds from both sides, at most the number and within one rounding of it, so a cleanup
  lowers it for good. Reaching one means a refactor first. A number is raised only when a
  planned stage of the work ends, by the maintainer who owns the plan, against that stage's
  planned size, never inside a fix. The rewrite is planned at about 62,000 shipped lines and
  550 tests. The enforced outer walls are 150,000 shipped lines and 1,000 tests;
  test lines have their own rounded ceiling, with no separate 150,000-line check.
  Shipped lines and the 1,500-line file cap cover `.rs` (and for the line total `.pest`)
  under `contextdb/src` and `contextdb-cli/src`, excluding `tests.rs`; `redb` and examples
  are outside those counts. Tests count every workspace nextest case, ignoring its default
  filter, plus one per SQL script; documentation and redb tests are outside that test count.
  Test lines count every file in `v2/*/tests` and all `tests.rs`, including redb.
  The exact current ceilings live in `check.yml`'s `SHIPPED_LINES`, `TESTS` and `TEST_LINES`
  environment entries; read them before changing code.
- It refuses a shipped file longer than 1,500 lines, a test-only name in shipped code, an
  ignored test, and an `allow` attribute beyond the seven named below.
- The lint settings above refuse a sleep, a thread, a clock read, a random id and a walk
  over a hash map.
| A killed writer opens by its recorded commit pages rather than reading every stored page | `contextdb/tests/crash/main.rs`: `a_killed_open_reads_the_log_and_last_commit_pages` |

## Do not add

- A second way to do one thing: there is one commit function, one expression evaluator, one `Error`.
- A test-only item in shipped code: no test-only name, feature or `pub` door; tests use what a user has.
- A check another part already makes: `write` checks a table's rules, `memory` says no, `store` only keeps.
- A lint switched off. Outside `redb/` there are seven `allow` attributes and they stay the only ones: the engine thread launcher in `contextdb/src/system/mod.rs`; `pause` in that file (the one place the engine sleeps, between tries of a wait the caller bounded); the machine clock in `contextdb/src/system/mod.rs` (the one place the time of day is read); the timer in `contextdb/examples/support/mod.rs` (measuring elapsed time is what the programs under `contextdb/examples/` are for); the shell's stdin-reader thread in `contextdb-cli/src/shell.rs` (it reads piped input beside the statements so Ctrl-C wakes an idle waiting run); and two in shared test support: the thread in `contextdb/tests/support/process.rs` (it moves a child's output lines to a channel so that a wait can give up), and `dead_code` in `contextdb/tests/support/mod.rs` (each test program uses only some helpers).

## Fast commands

Every command is run from the repository's root folder, the one that contains `v2/`. The local core check, then one Rust test, then one SQL script. The complete hosted
checks (including release instruction comparisons, scale and scheduled jobs) are in
[`README.md`](README.md#hosted-checks) and `check.yml`:

```sh
cargo fmt --manifest-path v2/Cargo.toml --all --check
cargo clippy --manifest-path v2/Cargo.toml --workspace --all-targets --locked -- -D warnings
cargo nextest run --manifest-path v2/Cargo.toml --workspace --locked
cargo test --manifest-path v2/Cargo.toml --workspace --locked --doc
cargo test --manifest-path v2/redb/Cargo.toml --locked --lib --tests
cargo +1.89 check --manifest-path v2/Cargo.toml --workspace --locked

cargo nextest run --manifest-path v2/Cargo.toml -p contextdb a_fresh_store_is_one_folder_and_works_with_no_configuration

SQL_SCRIPT=keys.sql cargo test --manifest-path v2/Cargo.toml -p contextdb --test sql
```
