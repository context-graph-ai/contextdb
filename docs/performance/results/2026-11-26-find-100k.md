# Performance result: find at 100,008 vectors on a 16-core desktop-class machine, 2026-11-26

## Promise

- Promise, in the product's words: "As a store grows, a vector search stays within the time the product promises". No figure promised for the time or for recall.
- Counted test that guards it: `a_hundred_thousand_sightings_are_found_with_the_recorded_work_recall_and_length` (`v2/contextdb/tests/find_at_scale.rs`, release build, every pull request) holds the vectors compared, the questions whose ten hold all of exact search's ten, and the data file's length at 100,000 generated sightings. `an_indexed_search_does_fewer_distance_evaluations_than_exact` (`v2/contextdb/tests/vectors_index.rs`) counts the vectors compared on a small store.

## Measurement

- Date: 2026-11-26 (02:07 to 03:25 UTC); revision measured: `672c10078a71d8b24a81ede80490bf979b0bcc79` (the script's header records one uncommitted file, a script fix made after the run began; the run used the committed script)
- Program and command: `v2/numbers.sh` with `PASSAGES`, `PASSAGES_LARGE` and `PASSAGES_LARGER` set (the passages program, `dump-large` import), `NUMBERS_LARGE=1`, `CAMERA_SECONDS=60`; lines `passages_100008_*` and `passages_165855_*`
- Data: 100,008 real search passages (and, in the last rows, 165,855), each a vector of 768 numbers and other columns, in eight partitions, sealed and grouped before searching; the ten nearest asked for, over one partition (`one`), several (`several`) or all (`all`); 100 questions; recall is the share of the recorded true ten nearest found, `all_ten` the questions that found all ten
- Passes and statistic: one run; p95 and p50 as the lines print them (passes per figure not recorded in the result lines); threads: 1
- Resources: engine memory limit: 1,073,741,824 bytes in the find sessions (the `_session` lines), threads 1; enforced process memory: not recorded; cores available: 16 (32 threads)
- Storage: ext4; temporary-store class and cache state not recorded
- Comparison: the previous figures are of `0c708a979e9eb5cbb1dca142f514edf96656711e` (2026-11-14, five runs, the median printed); this run is a single run on the same machine; the two revisions are not a controlled comparison (the data and the program were not held fixed)
- Machine: AMD Ryzen 9 9955HX, 16 cores and 32 threads, 59 GiB of memory (a desktop-class build machine, to itself during the run; not a user's machine); operating system: Ubuntu 26.04.1, Linux 7.0; Rust toolchain: unknown; user's machine: no
- Settings that can change the result: build rustflags none; popcount counting; index reader limit 1,073,741,824 bytes; index threads 1; search mode as named in each row

## Limitations

- Not like for like with 2026-11-14: the passages table now also declares Context Graph's own index for its search filter (`event_search_passages_active_idx` on context, generation, is_current and is_searchable, as Context Graph's schema declares it), without which this commit refuses the INDEXED cells, and the engine is the one merged since (pull request 29). The slower times and larger rows-read counts against 2026-11-14 are not yet explained; a run of both commits on the same schema is what settles it.
- Every p95 above that has a figure of 2026-11-14 is slower than the figure of 2026-11-14 on the same machine; automatic mode over all partitions is 49.452 ms against 4.027 ms, and it reads 12,702 rows at the median where the exact search reads 170. The cause was not looked for in this result.
- Recall of the all-partitions search is 0.9980 (98 of 100 questions found all ten) in indexed and automatic mode.
- A single run: the spread of a p95 across runs is unknown here.
- Time figures are of this machine and build only; no timed figure is a promise. Recall is over 100 recorded questions.
